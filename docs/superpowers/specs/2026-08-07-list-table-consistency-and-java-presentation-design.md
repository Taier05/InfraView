# 旧模块列表统一与 Java 展示优化设计

日期：2026-08-07

## 目标与范围

将主机、硬盘、MySQL、Redis 四个列表页统一为 Elasticsearch、RabbitMQ、Java 已采用的紧凑列表样式：每个单元格保持单行、所有展示列支持真实服务端升降序、表头不显示上下或双向排序箭头。后续新增列表模块延续本设计。

同时优化 Java 业务服务页：健康状态、端口状态、进程状态使用现有等级色；业务端筛选显示中文名称，但 API 查询和数据契约继续使用既有业务代码。

本次只调整只读展示、排序和参数白名单，不改变 Nightingale 固定查询、快照缓存、自动刷新、状态计算或只读安全边界，不增加 N+1 请求。

## 统一列表规则

- 表头、正文的字号、间距和行高对齐 Elasticsearch、RabbitMQ、Java。
- 每个单元格只显示一个单行值；长文本省略，完整内容通过原生 `title` 提示。
- 所有展示列均为排序按钮，但不渲染 `↑`、`↓`、`⇅` 等可见箭头。
- 排序按钮通过 `data-active`、`aria-label` 和 `title` 表达当前升降序；键盘操作能力不得退化。
- 表格超出窄视口时，只允许列表面板内的唯一横向滚动容器滚动，不允许页面级横向溢出。
- 每次切换排序字段或方向后回到第 1 页；排序状态继续写入 URL，刷新和分享后可恢复。
- 后续列表页以本节作为默认样式，不再新增另一套表头箭头、换行单元格或复合副指标样式。

## 列结构

### 主机

固定列顺序：

1. 主机名
2. IP 地址
3. CPU 核数
4. 内存容量
5. CPU 使用率
6. 内存使用率
7. 负载
8. IO 忙碌度
9. 网络发送
10. 网络接收
11. 运行时间
12. 状态

原“网络 出/入”拆为“网络发送”和“网络接收”。IP 地址、CPU 核数、内存容量和状态补充真实服务端排序。

### 硬盘

固定列顺序保持不变：

1. 主机
2. 设备
3. 型号
4. 容量
5. SMART 健康
6. 温度
7. 寿命
8. 通电时间
9. 错误摘要
10. 状态

“错误摘要”是经用户确认的保留例外，不拆成六个错误计数列。型号、SMART 健康和错误摘要补充真实服务端排序。

### MySQL

固定列顺序：

1. 实例地址
2. 版本
3. 角色
4. 连接
5. 活跃线程
6. QPS
7. TPS
8. 慢查询
9. Buffer Pool 容量
10. Buffer Pool 使用率
11. 复制状态
12. 复制延迟
13. 运行时间
14. 状态

“版本 / 角色”“QPS / TPS”“Buffer Pool 容量 / 使用率”“复制 / 延迟”分别拆列。“连接”是经用户确认的保留例外，单元格继续显示 `当前连接/最大连接`，不拆成两列。

### Redis

固定列顺序：

1. 实例地址
2. 角色
3. 内存上限
4. 内存使用率
5. 连接
6. 阻塞连接
7. QPS
8. 命中率
9. key 总数
10. 复制链路
11. 延迟
12. 运行时间
13. 状态

“QPS / 命中率”拆列。原连接单元格中的阻塞连接拆为独立列；“连接”仍显示 `当前连接/最大连接`，不拆成两列。

## 排序契约

- 所有排序均在 Service 中对完整筛选结果执行，再分页；前端不得只对当前页本地排序。
- 数值按未格式化的原始值排序，文本使用忽略大小写的自然排序。
- 主机网络发送、网络接收分别按对应速率排序；不再按两者之和排序。
- MySQL 连接和 Redis 连接沿用连接使用率排序；展示仍为 `当前连接/最大连接`。
- MySQL 版本按自然版本文本排序，角色使用固定角色顺序；QPS、TPS、Buffer Pool 容量、Buffer Pool 使用率和复制延迟分别按各自原始数值排序。
- MySQL 复制状态按其等级和固定状态顺序排序。
- Redis 角色、复制链路使用固定业务顺序；阻塞连接、命中率分别按原始数值排序。
- 硬盘 SMART 健康按等级顺序排序；错误摘要按所有可用错误计数之和排序，全部缺失才视为缺失。
- 页面状态列按有效展示等级排序，必须考虑采集等级覆盖，不能只比较原始状态字符串。
- 升序的等级顺序为正常、警告、严重、未知；缺失数值和缺失文本无论升降序始终置后。
- 主排序值相同后统一以稳定实体 ID 升序收口，避免刷新和分页时顺序抖动。
- 新排序字段必须加入前端 URL 校验、HTTP 参数白名单和 Service 查询白名单；未知、重复或非法参数继续返回安全 400。

响应 View 不增加仅为排序服务的字段；排序使用 Service 内已有领域数据。若某个显示值由多个原始量组成，只在本节明确规定的主值上排序。

## Java 展示规则

健康状态、端口状态、进程状态改为复用现有状态徽标或等价的等级色语义：

- 正常：绿色，等级为 `normal`。
- 异常：红色，等级为 `critical`。
- 暂无数据：灰色，等级为 `unknown`。

只改变这三个单元格的展示，不改变 Java 总体状态、状态来源、端口一致性或采集状态计算。

业务端筛选使用以下中文显示，并与业务端单元格的既有中文展示保持一致：

- `tikbee`：用户端
- `rider`：骑手端
- `mch`：商家端
- `saas`：管理后台端
- `mch_saas`：商家 PC 端

Java API 契约保持不变：服务项 `business` 继续返回映射后的展示名称，`available_names` 继续返回可筛选的原始代码。筛选 `<option>` 的 `value`、URL `name` 参数和 API 请求仍使用原始代码，仅 `<option>` 的可见 `label` 使用中文。未知业务代码原样显示，不猜测、不丢弃，确保向前兼容。

## 架构与兼容边界

- 前端继续复用 `ListPage` 控制栏、表格面板、空状态和分页结构，不引入第二套列表壳。
- 本次允许补充共享表格样式，但不进行七个模块的大规模共享组件重构。
- 后端只扩展现有查询枚举和比较函数；现有 API 路径、响应字段、分页和筛选契约保持兼容。
- 不新增 Nightingale 指标、PromQL、batch 查询或数据源调用，自动刷新仍复用现有快照。
- 页面和 API 继续只读，不提供详情写操作、运维按钮、任意查询或代理能力。
- 日志、测试和文档不得包含 Token、Cookie、认证头、Base URL、真实标识、地址、数量、容量、指标值或上游正文。

## 测试与验收

按 TDD 实施，至少覆盖：

- Service：每个新增排序字段的升序、降序、缺失置后、相同值稳定 ID 收口；状态使用有效展示等级；硬盘错误摘要求和；复合连接按使用率排序。
- HTTP：新增排序字段白名单、非法字段 400、分页顺序稳定且响应结构不变。
- 前端：四页精确表头与顺序、拆列后的单值、每个表头可排序、URL 切换、重置页码、无可见箭头字符。
- Java：三类状态的正常/异常/未知颜色，业务端筛选和单元格中文显示，原始查询值不变，未知代码回退原文。
- 样式：表格正文严格单行，长文本省略，窄视口只有表格容器横向滚动，既有 Elasticsearch、RabbitMQ、Java 样式不回归。
- 安全：无写 API、运维控件、任意 PromQL、N+1 或敏感信息输出。

最终实施验证包括相关 focused 测试、前端全量测试、typecheck、production build、Go gofmt/vet、全仓普通与 race 测试、编译、Playwright 静态发现、只读与敏感扫描。部署、重启、提交和推送均需遵守单独授权边界。

## 明确不做

- 不拆分主机之外未在本设计列出的新指标。
- 不拆硬盘错误摘要。
- 不拆 MySQL 或 Redis 的当前连接与最大连接。
- 不改变 Elasticsearch、RabbitMQ、Java 的列结构。
- 不增加图表、详情页、历史趋势、导出、写操作或运维能力。
- 不重构 Nightingale Provider、固定查询、缓存或 freshness 逻辑。
