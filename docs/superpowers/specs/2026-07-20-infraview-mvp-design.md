# InfraView MVP 设计规格

日期：2026-07-20

状态：已完成设计确认，等待仓库规格审阅

## 1. 背景与目标

InfraView 是一个轻量、只读的基础设施可视化平台。首期面向 Linux 服务器，通过统一 Web 页面展示基础设施状态。监控数据优先来自 Nightingale（夜莺），但系统不能让页面或核心业务逻辑绑定某个 Nightingale 版本，必须保留扩展其他数据源的能力。

MVP 的目标是交付一个可以通过 Docker Compose 运行、使用固定账号密码登录、适合 100 台以内 Linux 主机的只读平台。平台不执行远程命令，不提供修改、删除、重启等运维操作，也不自动变更服务器、服务或配置。

## 2. 设计原则

1. **只读优先**：业务能力仅包含查询与展示。登录和退出可以改变 Web 会话，但不能改变基础设施或监控系统。
2. **轻量部署**：生产环境只运行一个 InfraView 应用容器，不依赖业务数据库。
3. **数据源隔离**：页面只依赖 InfraView 领域模型，Nightingale 差异封装在适配器中。
4. **真实状态**：上游故障时明确展示过期数据或错误，禁止使用虚假零值伪装正常。
5. **可恢复开发**：持续维护项目状态、设计、TODO、部署和测试文档，使新上下文能从仓库恢复。
6. **不过度设计**：首版只实现总览、主机列表和单机详情，不加入告警、用户管理或自动化操作。

## 3. MVP 范围

### 3.1 页面

- 登录页。
- 基础设施总览。
- Linux 主机列表。
- Linux 单机详情。
- 数据源状态以导航状态和只读状态信息呈现，不提供在线配置页面。

### 3.2 指标

- 在线状态。
- CPU 使用率。
- 内存使用率。
- 系统负载。
- 磁盘容量使用率，详情页按文件系统展示。
- 磁盘读取与写入速率。
- 网络接收与发送速率。
- 运行时长。

### 3.3 时间与刷新

- 页面默认每 30 秒自动刷新。
- 保留手动刷新入口。
- 历史范围支持最近 1 小时、6 小时、24 小时、7 天。
- 时间范围切换或页面离开时取消不再需要的请求。
- 同类自动刷新请求尚未结束时，不叠加新请求。

### 3.4 主机列表

- 主机清单由数据源自动提供，InfraView 不维护独立资产清单。
- 支持主机名或 IP 搜索。
- 支持在线、离线状态筛选。
- 支持指标列排序。
- 支持分页。
- 不提供行级操作按钮。

### 3.5 明确排除

- 告警事件列表与告警规则管理。
- 用户、角色与权限管理。
- SSH、远程命令和脚本执行。
- 修改、删除、重启、发布、配置下发或任务调度。
- 监控历史数据持久化。
- 任意 URL、任意查询表达式或通用上游代理。

## 4. 用户体验与视觉

- 采用现代深色中文运维控制台。
- 卡片、趋势图与表格保持适中的信息密度，适合日常长时间查看。
- 导航、状态、指标解释和错误提示以简体中文为主。
- `InfraView`、CPU、I/O 等通用产品名和技术缩写保留英文。
- 使用低饱和深色背景，以蓝色为主色，绿色、黄色、红色分别表示正常、警告和危险。
- 状态不能只依赖颜色，必须同时提供文字或图形标识。
- 首版桌面端优先，同时保证常见平板宽度下基本可用。

## 5. 技术路线

### 5.1 后端

- 使用 Go 构建 HTTP 服务。
- 优先使用标准库 `net/http`、`log/slog` 和少量必要依赖。
- 负责配置、认证、会话、只读 API、数据聚合、缓存和数据源适配。

### 5.2 前端

- 使用 React、TypeScript 和 Vite。
- 使用 TanStack Query 管理页面查询、刷新、取消和状态。
- 使用 TanStack Table 实现主机表格、排序和分页。
- 图表采用 Apache ECharts，并只引入折线图、时间轴、提示框等实际需要的模块，避免加载无关图表能力。
- 不引入大型全套 UI 框架；使用 CSS 变量与项目组件形成统一深色主题。

### 5.3 交付形态

- 前端只在构建阶段需要 Node.js。
- 构建后的静态资源嵌入或复制到 Go 服务的静态资源目录，由同一 HTTP 服务提供。
- 使用多阶段 Dockerfile 构建，最终镜像只包含运行 InfraView 所需内容。
- 容器以非 root 用户运行。
- Docker Compose 暴露可配置 HTTP 端口，允许直接通过 `http://IP:端口` 访问。
- Nginx 或 Caddy 是可选外部组件，文档提供反向代理和 HTTPS 示例，但不作为默认依赖。

## 6. 总体架构

请求路径如下：

```text
浏览器
  │
  ├── 可选 Nginx/Caddy
  │
  ▼
InfraView 单一容器
  ├── React 静态页面
  └── Go HTTP 服务
      ├── 认证与会话
      ├── 只读 HTTP API
      ├── 总览与主机查询服务
      ├── 短期内存缓存
      └── 数据源适配器注册表
          ├── Mock 适配器
          ├── Nightingale 适配器
          └── 未来数据源适配器
```

InfraView 不包含数据库、任务队列、SSH 客户端、远程执行器或配置管理模块。

## 7. 模块职责

### 7.1 Go 模块

- `config`：读取并验证环境变量；运行时不允许页面修改配置。
- `auth`：固定账户校验、登录限速、随机会话令牌、认证中间件。
- `cache`：内存 TTL 缓存、旧数据保留和相同并发请求合并。
- `datasource`：稳定领域模型和数据源接口。
- `adapters/mock`：确定性开发与测试数据。
- `adapters/nightingale`：真实 Nightingale API 映射。
- `service`：总览聚合、主机查询、指标规范化、状态与阈值判断。
- `httpapi`：路由、参数校验、统一错误、安全响应头、日志和静态资源。

### 7.2 React 模块

- 登录与会话。
- 应用布局与导航。
- 总览页面。
- 主机列表页面。
- 主机详情页面。
- 数据源状态提示。
- 指标卡、状态徽标、趋势图、表格、时间范围选择器、骨架屏、空状态和错误提示等共享组件。

## 8. 数据源契约

数据源接口必须表达 InfraView 所需能力，而不是暴露某个监控系统的原始 API。接口包含：

- `Health`：读取数据源健康状态。
- `ListHosts`：读取规范化主机清单。
- `GetHost`：读取单台主机基础信息。
- `GetCurrentMetrics`：批量读取一组主机的当前指标。
- `QueryRange`：读取单台主机指定指标与时间范围的历史序列。
- `QueryAggregateRange`：按一组规范化指标键一次读取基础设施聚合历史序列，不接受主机 ID 哨兵值。

领域模型至少包含：

- 稳定的 InfraView 主机 ID。
- 主机名和 IP。
- 在线状态与状态时间。
- 可选操作系统和数据源元数据。
- 规范化指标键、数值、单位、时间戳与缺失状态。
- 历史序列的时间点和值。

适配器负责：

- Nightingale 内部标识与 InfraView 主机 ID 的映射。
- 原始字段和指标名称映射。
- 单位换算。
- 时间戳规范化。
- 批量查询。
- 将上游错误转换为统一错误类别。

页面不能接收或提交任意上游 URL、任意查询表达式或 Nightingale 原始请求体。

## 9. API 设计

首版 API：

- `POST /api/v1/session`：登录。
- `DELETE /api/v1/session`：退出当前会话。
- `GET /api/v1/session`：读取登录状态。
- `GET /api/v1/overview`：读取基础设施总览。
- `GET /api/v1/hosts`：搜索、筛选、排序和分页。
- `GET /api/v1/hosts/{id}`：读取主机基础信息和当前指标。
- `GET /api/v1/hosts/{id}/metrics`：按时间范围读取历史指标。
- `GET /api/v1/datasource/status`：读取数据源连接状态和最近成功查询时间。
- `GET /healthz`：Docker Compose 进程健康检查。

除登录与退出会话外，不设计改变服务器、服务、配置或监控系统状态的业务接口。

统一错误响应包含：

- 稳定的错误代码。
- 面向用户的简体中文信息。
- 请求 ID。
- 是否可重试。
- 数据是否来自过期缓存。

错误响应不得包含上游凭据、内部调用栈、原始敏感响应或未脱敏 URL。

## 10. 认证与安全

- 用户名和密码通过 Docker Compose 环境变量配置。
- 密码在服务端使用恒定时间比较，禁止写入日志。
- 登录成功后生成密码学安全的随机会话令牌。
- 会话仅保存在进程内存，容器重启后自动失效。
- 默认会话有效期 12 小时，可通过环境变量调整。
- Cookie 使用 `HttpOnly`、`SameSite=Strict` 和限定路径；HTTPS 场景支持启用 `Secure`。
- 登录失败按来源 IP 限速，默认每分钟最多 5 次。
- 默认不启用跨域访问，只支持同源页面。
- 设置内容安全策略、禁止 iframe 嵌入、禁止内容类型嗅探和合理的 Referrer Policy。
- 日志自动脱敏密码、令牌、Cookie、认证头和数据源凭据。
- 上游 HTTP 客户端设置超时、响应大小限制和默认 TLS 证书校验。

## 11. 缓存与数据流

浏览器每次只访问 InfraView API。认证中间件确认会话后，查询服务生成包含数据源、主机、指标、时间范围、步长和筛选条件的缓存键。

建议默认 TTL：

- 主机清单：60 秒。
- 当前指标：20 秒。
- 历史序列：60 秒。
- 数据源健康：15 秒。

所有 TTL 都允许通过环境变量调整。相同的并发缓存未命中请求必须合并，避免重复查询上游。主机当前指标必须支持批量读取；总览历史必须通过单次多指标聚合查询获得，禁止为总览按主机产生 N+1 请求或在浏览器生成历史数据。

历史查询根据时间范围自动计算步长，每条序列目标不超过约 600 个数据点，以限制响应体和浏览器绘图成本。

InfraView 不将监控数据写入磁盘。容器重启后缓存清空。

## 12. 阈值与状态

- 内置 CPU、内存和磁盘使用率的默认警告与危险阈值。
- 默认建议为 80% 警告、90% 危险。
- 阈值允许通过环境变量覆盖，页面不提供在线修改入口。
- 在线状态由适配器根据数据源语义确定，不能仅依据某项指标是否为零。
- 指标缺失必须表示为“暂无数据”，不能转换成数值零。

## 13. 上游故障与降级

- Nightingale 请求默认在 10 秒后超时并取消。
- 单项指标缺失只影响对应展示组件，不使整个页面失败。
- 上游失败且存在 5 分钟以内旧缓存时，可以返回旧数据。
- 返回旧数据时必须包含 `stale` 状态、数据时间，并在页面明显提示“数据已过期”。
- 没有可用旧缓存时返回标准 502 或 503 错误，页面显示错误和重试入口。
- 主机从数据源消失时，详情页显示“该主机当前不在数据源中”，不伪装成普通离线。
- Nightingale 故障不应导致 Docker 自动重启 InfraView。

## 14. 日志与健康检查

- 使用结构化日志。
- 请求日志包含请求 ID、路径、状态码、耗时、缓存命中状态和数据源类型。
- 不记录请求密码、Cookie、认证头、数据源令牌或完整敏感 URL。
- `/healthz` 只判断 InfraView 进程和内部 HTTP 服务是否正常。
- 数据源健康通过 `/api/v1/datasource/status` 与页面状态提示展示。
- 首版不额外部署日志系统、数据库或监控存储组件。

## 15. Docker Compose 与配置

Docker Compose 默认包含一个 InfraView 服务：

- 可配置监听地址和宿主机端口。
- 配置固定用户名和密码。
- 选择 `mock` 或 `nightingale` 数据源。
- 配置缓存 TTL、会话时间和资源状态阈值。
- 设置容器健康检查和重启策略。
- 不挂载 Docker Socket，不使用特权模式，不共享宿主机 PID 或网络命名空间。
- 默认不挂载可写业务数据卷。

部署文档提供两种访问方式：

1. 直接通过 `http://服务器IP:端口` 访问。
2. 使用已有 Nginx 或 Caddy 反向代理并启用 HTTPS。

## 16. 测试策略

### 16.1 Go

- 配置校验。
- 固定账户认证、会话和登录限速。
- 阈值与状态计算。
- 缓存命中、过期、相同请求合并和旧缓存降级。
- 数据源接口契约。
- Mock 适配器。
- HTTP 路由、认证、参数校验、错误响应和安全响应头。

### 16.2 React

- 页面加载、成功、空数据和错误状态。
- 搜索、状态筛选、排序和分页。
- 时间范围切换、自动刷新与请求取消。
- 过期数据提示和缺失指标展示。
- 状态不仅通过颜色表达。

### 16.3 集成与端到端

- Go HTTP 集成测试使用 Mock 数据源。
- Playwright 覆盖登录、总览、主机列表、主机详情和退出登录。
- Docker Compose 冒烟测试覆盖镜像启动、健康检查、登录和只读查询。
- 验证不存在基础设施写接口、远程命令入口或通用上游代理。

开发阶段遵循测试驱动方式：先增加失败测试，再实现最小功能，最后重构并运行完整验证。

## 17. 性能与验收标准

- Docker Compose 可以用一条命令启动。
- 可以通过 IP 和端口登录并使用全部 MVP 页面。
- 可选反向代理不会要求改变应用构建方式。
- Mock 模式功能完整，数据确定且适合自动化测试。
- 支持 100 台以内主机。
- 缓存命中 API 的目标 P95 响应时间小于 200 ms。
- 单 InfraView 容器空闲内存目标低于 256 MB。
- 自动刷新不产生重叠请求风暴。
- 上游不可用时能明确展示旧数据或错误。
- 自动化测试、生产镜像构建和 Docker Compose 冒烟测试全部通过。

## 18. 两阶段交付

### 18.1 里程碑 1：Mock 数据源 MVP

交付认证、总览、主机列表、主机详情、缓存、深色中文 UI、自动化测试、Docker Compose 和完整文档。Nightingale 接口边界和配置入口就位，但不猜测未知 API。

### 18.2 里程碑 2：真实 Nightingale 集成

测试环境就绪后：

1. 只读确认版本、认证方式和 API。
2. 记录主机、当前指标和历史序列的字段与单位映射。
3. 创建完全脱敏的响应夹具。
4. 实现 Nightingale 适配器和契约测试。
5. 验证批量查询、超时、错误、缓存和降级。
6. 更新兼容性、配置和部署文档。

这一阶段不改变前端页面和核心服务架构。

下一份详细实施计划只覆盖里程碑 1。里程碑 2 必须等待测试环境信息明确后单独编写集成规格与实施计划，禁止在当前计划中猜测 Nightingale API。
