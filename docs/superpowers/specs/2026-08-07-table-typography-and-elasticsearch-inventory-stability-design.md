# 列表字体统一与 Elasticsearch Inventory 稳定性设计

日期：2026-08-07

## 目标与范围

本次交付同时解决两个已由现有 8080 视觉验收发现的问题：

1. 主机、硬盘、MySQL、Redis 虽已使用紧凑列表结构，但表头、正文、行高、内边距和状态徽标仍与 Elasticsearch、RabbitMQ、Java 存在可见差异。
2. 只有 Elasticsearch 会间歇显示“数据已过期”“刷新失败/加载失败”以及“采集延迟/采集失联”，RabbitMQ 等同为 15 秒采集周期的模块未出现同类抖动。

本次只调整列表排版样式与 Elasticsearch Nightingale Provider 的 inventory 归并。现有列数、排序、筛选、分页、固定查询、缓存时长、2/5 周期 freshness、只读 API 和安全边界保持不变。

## 只读调查结论

### 列表排版差异

七个列表页都以 `host-table` 为基础，但当前实际使用了多套覆盖规则：

- RabbitMQ 与 Java 的表头、正文和横向内边距分别使用同一组紧凑值。
- Elasticsearch 使用一组非常接近但不完全相同的值。
- MySQL 与硬盘仍使用更大的字号和内边距。
- 主机与 Redis 主要继承更大的 `host-table` 默认值。
- 个别内部元素继续覆盖字号、字重或状态徽标尺寸。

因此当前仅统一了列表壳、单行和无箭头结构，没有统一最终计算样式。

### Elasticsearch 独有的 inventory 归并问题

Elasticsearch 的两组 inventory 使用 24 小时历史查询。返回值中：

- 外层时间是本次即时查询的执行时间；
- 指标值是 inventory 的真实上报时间。

同一批次返回的多条历史序列通常具有相同的查询执行时间，但真实上报时间可以不同。当前 Elasticsearch Provider 使用查询执行时间判断候选新旧；同一稳定集群或节点只要出现“查询时间相同、真实上报时间不同”的历史序列，就会被当成冲突，并令整个快照返回 `ErrUnavailable`。

RabbitMQ 的历史 inventory 不同：它使用真实上报时间选择最新候选，忽略旧候选；非法或冲突候选只影响对应实体，不会让无关实体和整个快照一起失败。

Elasticsearch 当前行为可以完整解释现场现象：

1. 已有缓存时，本次 Provider 失败会回退旧快照并设置 `meta.stale=true`，页面显示“数据已过期”。
2. 容器刚启动或没有可用缓存时，同一失败直接表现为加载/刷新错误。
3. 连续没有成功快照时，inventory 进度不推进，现有 freshness 会进一步显示采集延迟或采集失联。
4. 下一次返回的候选组合未触发整快照冲突时，页面立即恢复。

因此不采用 Elasticsearch 专属的 UI 隐藏、延迟告警或额外重试。那只会掩盖 Provider 根因，并让 Elasticsearch 与其他模块产生新的行为差异。

## 统一列表排版契约

### 共享类

Elasticsearch、RabbitMQ、Java、主机、硬盘、MySQL、Redis 七个表格统一增加 `observability-table` class。`host-table` 继续提供基础表格结构；`observability-table` 成为所有当前及后续观测列表的唯一排版基准。

共享规则明确锁定：

- 表头和单元格内边距：`0.3rem 0.18rem`。
- 表头字号：`0.62rem`。
- 表头字重：`750`。
- 表头行高：`1.1`。
- 正文字号：`0.69rem`。
- 正文字重：`500`。
- 正文行高：`1.25`。
- 状态徽标字号：`0.66rem`。
- 状态徽标间距：`0.2rem`。
- 状态徽标内边距：`0.14rem 0.26rem`。
- 状态圆点：`0.36rem × 0.36rem`。
- 表头和正文都保持单行；超长值在所属单元格内截断。

七页的状态单元格必须复用相同的计算样式。主机现有自定义状态元素可以保留语义 class，但其字体、间距和圆点必须由共享规则归一，不能继续形成另一种视觉。

### 允许保留的页面差异

以下内容仍由模块专属 class 控制：

- 每列宽度与表格最小宽度。
- 窄视口下的唯一横向滚动阈值。
- 身份字段使用省略号还是裁切。
- 正常、警告、严重、未知等语义颜色。
- 不同数据类型的格式化文本。

模块专属 CSS 不得重新声明字号、字重、行高、表头/单元格内边距或状态徽标尺寸。Elasticsearch 当前接近基准的专属排版值也一并删除，确保七页最终计算样式完全相同。

本次不改变页面标题、说明、搜索、筛选、每页数量、采集时间、空状态、错误面板或分页控件的样式。

## Elasticsearch Inventory 归并契约

### 候选解析

两组必需 inventory 继续使用现有固定查询和同一次 26 组即时 batch，不新增查询、重试或 N+1。

每条候选必须先解析：

- 稳定领域身份；
- 真实上报时间；
- 节点可选地址。

查询执行时间只用于验证响应形状，不再用于同一领域身份的候选新旧排序。候选新旧唯一使用真实上报时间。

单条候选缺少稳定领域身份或时间非法时局部忽略。不得使用 `ident`、实例地址或采集目标推测集群名、节点名或构造替代身份。

### 集群 inventory

集群继续只以明确的集群名建立稳定身份：

- 首个合法候选建立状态。
- 更晚真实上报时间的候选替换旧候选。
- 更早候选直接忽略。
- 相同最新真实上报时间的等价候选安全去重。
- 输入顺序不得影响结果。

### 节点 inventory

节点继续只以明确的集群名和节点名建立稳定身份：

- 更晚真实上报时间的候选整体替换旧候选。
- 更早候选直接忽略。
- 相同最新真实上报时间且地址一致时安全去重。
- 相同最新真实上报时间但地址冲突时，保留节点身份并将地址置空，由页面显示“暂无数据”；不得猜测地址，也不得令整个快照失败。
- 输入顺序不得影响结果。

### 必需组与失败边界

以下情况仍安全返回 Elasticsearch 数据源不可用：

- batch 组数不等于固定数量；
- 任一必需 inventory 组为 `null`；
- 集群 inventory 完全没有可用稳定身份；
- 节点 inventory 完全没有可用稳定身份；
- 上游请求、协议、认证、超时或响应 envelope 不合法。

第 1–24 组可选观测指标的单组 `null` 继续只表示该项暂缺。单个无效或过时 inventory 候选不得再拖垮同组其他有效实体。

## Freshness、stale 与错误语义

- Elasticsearch 的 `SnapshotTTL`、`MaxStale` 和预期采集周期保持不变。
- 集群与节点继续独立跟踪 inventory 的真实上报时间。
- 继续使用现有 2 周期警告、5 周期严重规则；不放宽真实采集延迟或失联判断。
- `clusterinfo_up`、`node_stats_up` 和集群健康的现有状态语义保持不变。
- Provider 真正失败时仍按现有缓存规则返回 stale 或安全错误；页面继续立即如实展示。
- 不增加前端自动 retry、不延迟横幅、不修改全局 QueryClient。

修复后的目标不是隐藏告警，而是让正常的新旧历史 inventory 不再被误判为整快照失败。

## 测试设计

### Provider RED→GREEN

新增脱敏 fixture 测试，至少覆盖：

- 同一集群的旧、新历史候选具有相同查询执行时间、不同真实上报时间；新候选胜出。
- 同一节点的旧、新历史候选按真实上报时间选择，且正反输入顺序结果一致。
- 最新节点候选携带最新地址时正确替换旧地址。
- 相同最新时间、不同地址时仅清空地址，节点仍保留。
- 单个非法候选与合法候选并存时，仅忽略非法候选。
- 必需组为 `null` 或整组没有可用身份时仍返回安全 `ErrUnavailable`。
- 错误不包含 Token、认证头、Base URL、查询文本或上游正文。
- 仍恰好一次固定 26 查询 batch。

### Service 与 HTTP 回归

- 正常重复历史 inventory 能持续生成成功快照，并推进集群和节点 freshness。
- 正常新旧候选不产生 `meta.stale`、采集延迟或采集失联。
- 真正 Provider 失败仍返回 stale 深拷贝；无缓存时仍返回安全 503。
- View、API 字段、筛选、排序、分页、采集时间和写方法拒绝保持不变。

### 前端与样式

- 七个列表表格都必须带 `observability-table`。
- 测试以手写预期锁定共享排版 token，不从生产常量复制期望值。
- 页面专属 CSS 不得覆盖共享字号、字重、行高、内边距和状态徽标尺寸。
- 七页列数、表头、排序键、无可见箭头、单行单值、唯一滚动容器保持不变。
- Elasticsearch stale、错误和采集状态展示测试保持现有真实语义，不新增静默窗口。

## 验证与验收

实施时按 TDD 完成定向 RED→GREEN，并运行：

- Nightingale Elasticsearch Provider、Service、HTTP focused 普通与 race 测试。
- 七个相关前端页面测试、共享组件测试和 typecheck。
- 前端全量测试、production build、Playwright 静态发现。
- Go gofmt、vet、全仓普通/race 测试与 Linux 编译。
- 固定查询数量、单 batch、只读方法、敏感模式、whitespace 与 Git 范围扫描。

若用户后续单独授权部署，只原位重建现有 8080，继续复用既有测试 Nightingale 私密配置，不创建额外端口。现场验收只输出固定布尔结论，不读取或输出真实实体、标识、地址、数量、容量、指标值或上游正文。

## 明确不做

- 不修改 Elasticsearch 固定 PromQL、查询数量或查询顺序。
- 不增加 Provider、Service 或前端重试。
- 不隐藏或延迟真实 stale、错误、采集延迟或采集失联提示。
- 不改变其他模块的数据源、缓存或 freshness 逻辑。
- 不改变七页列结构、排序、筛选、分页或 API View。
- 不新增详情、图表、导出、写 API、运维控件、任意查询或代理能力。

本设计针对性修订 `2026-08-07-list-table-consistency-and-java-presentation-design.md` 中“不重构 Elasticsearch Provider、缓存或 freshness 逻辑”的旧范围：只允许上述 inventory 候选归并修复；缓存和 freshness 本身仍不修改。
